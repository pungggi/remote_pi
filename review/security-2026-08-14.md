# Security review — remote_pi (Piper) monorepo

**Date:** 2026-08-14 · **Scope:** `relay/` (Rust), `pi-extension/` (Node/TS), spot checks of `app/`, `cockpit/`, repo hygiene · **Reviewer:** agent-assisted code review, static analysis only (no fuzzing, no dependency CVE scan beyond versions in manifests)

---

## Threat model as implemented

- Identity = Ed25519 keypairs. WS auth = challenge–response (fresh 32-byte nonce, sig over nonce). The relay **admits any self-generated key** — there is no allowlist; pairing/authorization happens at the Pi (`peers.json`).
- Message channel phone ⇄ Pi is **plaintext JSON inside base64** (`PlainPeerChannel`). No inner cipher, no inner signature (E2E was rolled back — plan 06).
- Trust anchors: (a) the relay operator, (b) TLS if `https://` is configured, (c) OS keyring on each end. Default topology is a self-hosted relay on the LAN dialed over **`ws://`**.

---

## Findings

### HIGH

**H1. No end-to-end encryption or end-to-end authentication between phone and Pi.**
`pi-extension/src/transport/peer_channel.ts` (header comment: *"`ct` is base64(JSON.stringify(inner)) — no cipher, no MAC"*); decode in `index.ts` ~L1570 and `_handlePairRequest`.
The relay never needs to "decode `ct`" — it is already plaintext. Consequences if the relay is compromised, malicious, or MITM'd (see H2):
- Read all chat, code context, tool traffic, images.
- Impersonate the paired owner (the relay asserts sender identity via the `peer` rewrite — a relay can forge that trivially) → inject `user_message` turns (prompt injection into an agent with shell access), fire `open_terminal_request`, `start_session_request`, `remove_worktree_request` (`git branch -D`), `session_sync` history reads.
- Several comments ("relay never decodes `ct`", "Relay continues opaque") read as if confidentiality existed; they describe base64 opaqueness only. `config.ts` documents the "no public relay" reasoning honestly, but the wire format itself provides zero protection.

*Recommendation:* minimum viable fix — **sign each inner envelope** with the Owner Ed25519 key (both sides already have long-term keys; verify against `peers.json` before routing actions). Better — restore the planned X25519/Noise inner encryption (plan 04 had the design). Also state the trust model in PROTOCOL.md in one explicit paragraph.

**H2. Default LAN path is plaintext `ws://` — full owner powers for a network MITM.**
`relay/src/lan.rs` advertises `http://ip:port` in the challenge; `config.ts` `toWebSocketUrl` maps `http://`→`ws://`; the Rust relay serves plain WS (no TLS termination). The QR embeds the `ws://`-reachable address (`buildQRUri` `r` param).
On an untrusted WLAN (café/hotel/corporate), an ARP-spoofing attacker holds the phone's authenticated WS: read everything, and send any owner action — including spawning a terminal running `pi` at any existing path (H4 chain). The "home WLAN is trusted" assumption is documented but nothing warns the user when the phone dials a non-RFC1918 or unknown network over `ws://`.

*Recommendation:* support `wss://` on the LAN relay with a self-signed cert pinned via the QR (TOFU); until then, surface a persistent banner in the app when connected over an insecure `ws://` transport.

### MEDIUM

**M1. Relay metadata disclosure: presence/rooms of arbitrary pubkeys, no authorization.**
`relay/src/handlers/peer.rs` — `subscribe_presence` / `subscribe_rooms` / `rooms_check` / `presence_check` accept arbitrary target pubkeys from **any** authenticated peer (any self-generated key). `registry.rooms_of()` returns full `RoomMeta` including **`cwd`**, machine session `name`, `model`, `thinking`, `git` snapshot. On a shared relay/overlay (the recommended Tailscale topology), any other member who learns a victim's pubkey can track online/offline times and read those metadata fields.
Mitigations in place: the pubkey is a 128-bit secret unless leaked; mesh GET is hash-gated. Still, the `mesh_auth` machinery (plan 25) already computes exactly "these two pubkeys share an Owner" — reuse it to gate presence/rooms subscriptions.

**M2. Relay DoS surface.**
`relay/src/handlers/peer.rs` + `main.rs`:
- No connection cap, no rate limit, no per-peer room cap; `mpsc::unbounded_channel` per conn; `forward_to_all_rooms_of` clones to every conn.
- WebSocket `max_message_size` is not configured (axum/tungstenite default ≈ 64 MiB message). Outer envelopes are capped at 4 MiB via `parse_line` (`protocol/outer.rs`), but **`pi_envelope` control frames bypass that cap entirely** (`handle_pi_envelope` forwards the `envelope` object verbatim with no size check) — a single authenticated peer can push ~64 MiB JSON through `serde_json` parse + verbatim forward repeatedly.
- Every text frame (including outer envelopes) is `serde_json::from_str`'d once as `Value` before the (second) `parse_line` parse — double parse cost per message.

*Recommendation:* set `.max_message_size()` on `WebSocketUpgrade`, apply the same 4 MiB cap to `pi_envelope`, cap rooms/conns per peer and per IP, and skip the `Value` parse when the line starts with `{"peer"`/is not an object with `"type"`.

**M3. Remote action chain can reach code execution with a malicious cwd.**
`actions/open_terminal.ts` (`handleOpenTerminal` accepts any *existing* `msg.cwd`; creates worktrees, deletes branches), `actions/start_session.ts` (`handleStartSession` spawns `pi --mode rpc` at any `msg.cwd` via the supervisor). Pi auto-loads project-local `.pi/` config/extensions/skills from the cwd → spawning `pi` inside an attacker-chosen directory (e.g. a cloned malicious repo) is arbitrary code execution. Requires a malicious/compromised relay (H1), a network MITM (H2), or a phished pairing QR — but there is no second gate.
*Recommendation:* restrict both actions to the configured `projects.roots` (already exist in config) or previously-registered cwds; require explicit confirmation for unknown roots; consider disabling project-local extension auto-load in RPC/daemon mode.

**M4. UDS broker / supervisor sockets rely on umask for access control.**
`session/global_config.ts` `ensureGlobalDirs()` / `saveConfig()` create `~/.pi/piper` and `sessions/` with default mode (0777 & ~umask → typically 0755). The broker socket `~/.pi/piper/sessions/local/broker.sock` and `supervisor.sock` get default socket perms (typically 0755 → connect requires owner write, so effectively single-user **only when umask is 022**). Under umask 0 (containers, some CI/launchd contexts) any local user can connect, register a peer, inject envelopes into every agent session (prompt injection), and read the roster. `storage.ts` already does this correctly for the identity file (mkdir 0700 + chmod) — replicate for the sessions/supervisor dirs and explicitly chmod the socket file. On Windows, named pipes (`ipc.ts`) get default DACLs — verify same-user-only connect (libuv behavior) before trusting it.

**M5. Unauthenticated local roster disclosure.**
`session/broker.ts` `_tryObserverProbe()` — an *unregistered* UDS connection may send `list_peers` and receives the full roster: peer names, **cwd paths**, cross-PC labels. Combined with M4 this is an information leak even when connect is possible. Require registration (or drop the observer path) and gate on the tightened socket perms.

### LOW

**L1. `GET /mesh/:hash` and `/health` are unauthenticated.** Anyone who can reach the relay and knows the 256-bit owner hash can fetch the mesh blob (member pubkeys, relay URLs, paired_at). Hash-as-capability mitigates; acceptable, but binding `/mesh` to loopback or requiring a token would close it. `POST /mesh` is properly signature-verified (`verify_strict`), hash-bound, monotonic-versioned, body-capped (500 KB) — solid.

**L2. No timeout on the auth step.** `peer.rs` wraps `hello` in a 5 s timeout but the subsequent `auth` frame `stream.next().await` is unbounded → half-handshaked sockets can linger. Wrap it in the same timeout.

**L3. QR dictates the relay (`r=` param), phone adopts it on pair.** A phished/crafted QR pairs the phone to attacker infrastructure (plaintext by design). The app already detects relay mismatch for legacy QRs; consider showing the relay hostname prominently in the pre-pair confirmation screen.

**L4. Pairing token comparison is not constant-time** (`qr.ts` `consumeToken`). Negligible in practice (128-bit token, 60 s window, single-use over WS) — noted for completeness.

### Positive notes (verified during review)

- Relay: nonce-signed challenge–response; forced `peer` rewrite on outer envelopes (anti-spoof); `pi_envelope` gated on signed mesh membership with bounded TTL cache; `verify_strict` for mesh blobs; parameterized SQL only; poison-recovery on mutexes; version-monotonic upserts; `pi_forward` synthesized transport errors never echo attacker JSON verbatim.
- Broker: forces `env.from` to the registered address (local anti-spoof); cross-PC `from` rewritten from the relay-verified `from_pc` + mesh-sibling check (`broker_remote.handleIncoming`); remote inject is unicast-only, parse-validated; bounded peer caps (`peer_limits.ts`).
- Key handling: platform keyring with a careful locked-keychain policy; file fallback 0600/0700; no-fork-namespace migration (explicitly avoids hijacking upstream's keytar entries).
- Image pipeline: strict RFC-4648 base64, MIME whitelist + magic sniffing, 10 MB cap, sanitized filenames, temp dirs.
- Repo hygiene: `.gitignore` covers `*.log` and `/data/`; no secrets found in tracked files or the stray `_throw*.log` working-tree dumps (untracked — consider deleting anyway).

## Resolution status (2026-08-14)

Fixes 1–5 of the priority list were implemented same-day — see
[`plan/130-security-fixes.md`](../plan/130-security-fixes.md). Summary:

1. ✅ **Inner-envelope signatures** — outer `sig` field (Ed25519 over
   domain-prefixed `ct` with the WS-handshake key), relay-forwarded verbatim,
   verified Pi↔App, with a per-peer `signing` ratchet (peers.json /
   PeerRecord) that drops unsigned frames once a peer has demonstrated
   signing. Transition-safe for old clients.
2. ✅ **Insecure-transport banner** (banner option) — persistent Home banner
   while Online over non-TLS non-loopback transport; full `wss://` + QR pin
   deferred to a follow-up plan.
3. ✅ **Relay caps** — 5 MiB WS message/frame ceiling, 4 MiB `pi_envelope`
   cap with `too_large` transport error, 5 s auth-step timeout.
4. ✅ **Presence/rooms mesh-gating** — cross-peer metadata queries now
   require shared Owner membership (`MeshAuthCache`), self always allowed.
5. ✅ **Local hardening + cwd policy** — `~/.pi/piper` 0700 + sockets 0600;
   `open_terminal`/`start_session` cwds restricted to `projects.roots` or
   registered worktrees.

## Priority fix order (original)

1. Inner-envelope signatures (Owner key) — closes impersonation even with an honest-but-curious relay; keys and peers.json already exist. (H1)
2. `wss://` + pinned cert for LAN, or at least an insecure-transport warning in the app. (H2)
3. Relay hardening: message-size cap on `pi_envelope`, `max_message_size`, auth timeout, room/conn caps. (M2, L2)
4. Gate presence/rooms subscriptions behind `mesh_auth`. (M1)
5. 0700 on `~/.pi/piper` (+ sessions dir) and explicit socket chmod; verify Windows pipe DACL. (M4, M5)
6. Restrict `open_terminal` / `start_session` cwds to configured project roots. (M3)
